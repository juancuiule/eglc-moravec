# Backend re-validates trial correctness/timing; supersedes ADR-0002

ADR-0002 deferred server-side re-validation because it meant re-deriving `operations/`'s solve-time rules on the backend — real duplicated logic, not just duplicated types — and named that specific need ("the backend needs `operations/`-level scoring knowledge") as its own trigger for extracting a shared `engine` package (ADR-0001). Both conditions have now genuinely fired: `packages/engine` exists (ticket 01), and the sync payload carries each trial's operands and submitted answer (ticket 04), so the backend can reconstruct the exact `Operation` a trial was and re-score it with `engine`'s own `evaluateTrial` — the same rules the client itself uses.

`POST /sync/results` now recomputes `correct`/`timeExceeded` for every incoming trial from its operands, answer, and reported `timeTaken`, independent of what the client claims. The server's own computed values are what get stored in `trial_results.correct`/`time_exceeded` — the columns everything analytical (admin stats included) already reads — while the client's original claim is kept alongside in new `client_correct`/`client_time_exceeded` columns, for comparison and future auditing, not discarded.

A disagreement between the two is not an error: the sync still succeeds, nothing is surfaced to the player, and nothing about this corrects or overrides a player's own local `LevelStats`/history — this is a backend-internal integrity signal only, per the "real purpose" grilling session. Timing itself is still client-reported (`timeTaken` is not independently measured by the server); that remains a separate, larger problem than re-scoring correctness from already-known operands and an already-known duration.
