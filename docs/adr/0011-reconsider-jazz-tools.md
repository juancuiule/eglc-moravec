# Reconsidering Jazz.tools for local-first sync

CONTEXT.md carries one line on this: "Jazz.tools was evaluated for local-first sync and rejected — noted here so it isn't re-evaluated from scratch; if local-first sync work resumes, revisit that verdict rather than assuming it still holds, since neither the tool nor this app's sync needs are static." That's genuinely all that survives — no ADR mentioning Jazz exists anywhere in git history, including deleted ones (`git log --all` across every `docs/adr/*` path ever committed turns up zero mentions of "jazz" in file content). **This document does not reconstruct or guess at the original rejection reasoning.** The closest thing to a timing anchor is the cluster of sync/accounts ADRs that were being written when that CONTEXT.md line was presumably added: ADR-0002 through 0005 and the keystroke-sync/server-integrity work landed 2026-08-22, and ADR-0008/0009/0010 (anonymous accounts, levels-to-backend) landed 2026-08-23 — all within two days of today (2026-08-24). So "evaluated and rejected" was almost certainly a very recent call, not a stale one from months ago. That matters: it means whatever "too soon" meant, it was said about Jazz as it exists *now*, or something very close to it — not about a materially older product.

**Verdict: still too soon, but not for a hand-wavy reason — track it, don't adopt it, and set a concrete trigger to revisit.** The single biggest new fact this research surfaced, one that a rejection even a week old couldn't have accounted for: Jazz is currently two different products wearing one name, and neither is in the position you'd want for a small, single-maintainer, self-hosted app to bet its data layer on. The architecture-level fit turned out to be *better* than a skeptic would expect — server-side re-validation and anonymous-to-real identity upgrade are both real, first-class, well-documented patterns, not workarounds. That's the strongest argument for reconsidering. But production-readiness is the strongest argument against, and it's not a close call either way once you look at what the vendor itself says.

## 1. What Jazz.tools is today, and how it describes its own readiness

Jazz.tools is currently split across two products. **"Classic Jazz"** (`garden-co/classic-jazz` on GitHub) is the original CoValue/CRDT-based local-first database — 2,534 stars, 111 forks, created August 2023, still receiving releases (`jazz-tools@0.20.19` shipped 2026-07-03) but at a visibly slowed cadence (the prior release, `0.20.18`, was 2026-04-30 — roughly a two-month gap, versus much tighter cycles earlier in its history per the npm registry's publish timestamps). It has a real, if small-scale, production track record: the [showcase page](https://classic.jazz.tools/showcase) lists thirteen shipped apps (Opacity, Invoice Radar, Tilly, Learn Anything, and others), all indie/small-team scale — a comparable weight class to this project.

**Jazz v2** (`garden-co/jazz` on GitHub, created January 2026, 175 stars, 17 forks) is what `jazz.tools` now shows by default. It's described by its own author as ["a fairly radical departure from Jazz v0.x"](https://jazz.tools/blog/what-we-learned-from-classic-jazz): permissions moved from cryptographic, client-enforced Group rules to ["a trusted server applying richer policies at sync time"](https://jazz.tools/blog/what-we-learned-from-classic-jazz); the CRDT replay history model became a ["more git-like model of snapshot DAGs"](https://jazz.tools/blog/what-we-learned-from-classic-jazz); and the CoValue/local-JSON API became an ["ORM-like query shape"](https://jazz.tools/blog/what-is-jazz) over relational tables. The npm registry shows 49 `2.0.0-alpha.x` releases between roughly January and July 2026, most recently `2.0.0-alpha.53` on 2026-07-10 (`https://registry.npmjs.org/jazz-tools`, `dist-tags`/`time` fields) — an active but not currently red-hot cadence as of today.

Jazz's own words on where v2 stands, from its ["What is Jazz?"](https://jazz.tools/blog/what-is-jazz) post (dated 2026-04-18): **"Jazz is still alpha-quality software and infrastructure"**, and adopting it means being able to **"tolerate an evolving API and a best-effort SLA."** The same post names its intended audience explicitly: **"Jazz is best suited to small teams building new apps that are collaborative, real-time, local-first, agent-heavy, or otherwise unusual enough to really benefit from its architecture"** — which, read charitably, actually describes this project reasonably well. But it also says larger or commercial adopters are **"onboarded selectively, in close partnership"** rather than through a standard self-serve path, and the vendor's explicit commitment to classic Jazz is to keep it patched and its cloud running **"until everyone has had a fair chance to migrate"** ([same post](https://jazz.tools/blog/what-we-learned-from-classic-jazz)) — i.e., classic Jazz is maintained but has a stated end state of being superseded, not a product with an indefinite-support commitment either.

So: classic Jazz is mature but on a glide path to deprecation; v2 is the vendor's actual present-tense focus but says of itself, in its own launch post, that it isn't done being alpha software. Neither status is what "not too soon anymore" would look like.

## 2. Server-side re-validation of trial correctness — the load-bearing question

This is not a dealbreaker for either Jazz product, which is the most useful finding in this whole research pass — a plausible worry going in ("Jazz's model is cryptographic client-CRDT-merge-is-final, full stop") turns out to be wrong for both versions, just for different reasons.

**Jazz v2** enforces permissions **server-side**, not just cryptographically client-side: ["Jazz enforces them server-side using row-level policies defined in `permissions.ts`. Clients that fail a policy check have their writes rejected and their reads filtered."](https://jazz.tools/docs/auth/permissions) A backend process gets a privileged, unrestricted handle via `context.asBackend()` — writes from it are authored as `jazz:system` — separate from `context.forRequest(req)`, which runs scoped to the calling user's own permissions (`https://jazz.tools/docs/getting-started/server-setup#backend-context-setup`). Update policies can also distinguish the row *before* and *after* a write (`.whereOld(...)` / `.whereNew(...)`), which the docs show being used specifically to lock down which columns a client is allowed to touch at all (`https://jazz.tools/docs/auth/permissions#update-policies-old-row-vs-new-row`). Put together, the natural shape for this app's re-validation requirement is: the client inserts a row with its raw operands/answer/`timeTaken` and its own claimed `client_correct`/`client_time_exceeded`; permission policy denies the client write access to `correct`/`time_exceeded` entirely; a backend worker, running as `context.asBackend()`, observes the insert, recomputes correctness with `packages/engine`'s own logic exactly as `apps/backend/src/sync/logic.ts` does today, and writes those columns itself. That is a direct, idiomatic fit for what this app already does — it isn't a workaround.

**Classic Jazz** gets to roughly the same place through a different, more manual mechanism. A [Server Worker has no inherent privilege](https://classic.jazz.tools/docs/react/server-side/setup) — **"server code doesn't have any special or privileged access to the user data. You need to be explicit about what you want to share with the server"** and **"your server workers will have their own accounts, and they need to be explicitly given access to the CoValues they need to work on."** Access is governed by Group roles, and classic Jazz's role set includes a `writeOnly` role described as **"Blind submissions"** — ["users can only create/edit their own updates"](https://classic.jazz.tools/docs/react/permissions-and-sharing/overview) — which maps well onto "a player can submit a trial result but can't see or edit anyone else's, and can't touch the server's verified fields." The pattern would be: players hold `writeOnly` on a shared CoList/CoMap for their own raw submissions; the server worker holds `writer`/`admin` and owns a separate CoValue (or separate fields) for the verified `correct`/`time_exceeded`. This works, but it has to be modeled deliberately — classic Jazz has no declarative "server owns this column, clients can't touch it" policy primitive the way v2 does; it's achieved by keeping client-writable and server-writable data in genuinely separate Groups/CoValues rather than by a permission rule on a shared field. The docs available did not directly state whether two peers both holding write access to the *same* field resolve via plain last-writer-wins if that separation isn't maintained, so treat that as an open risk to verify hands-on rather than something confirmed by primary sources here.

Bottom line for Q2: **both versions support a real "trusted backend observes and independently verifies" pattern**, not just terminal CRDT merge. v2's version of this is more explicit and declarative; classic Jazz's requires more careful schema/Group design to get the same guarantee. Either way, this specific worry — arguably the reason a bespoke sync layer looked safer before — is less of an obstacle than it would have appeared without digging in.

## 3. Self-hosting the sync server on a home LAN / Docker Compose box

Both products are self-hostable without depending on Jazz Cloud, and the vendor is explicit about intending that to remain true: **"The single-tenant Jazz database server will always be open-source and is very easy to self-host"** ([jazz.tools/](https://jazz.tools/)).

For v2, self-hosting is one process: `npx jazz-tools@alpha server "$JAZZ_APP_ID" --port 1625 --data-dir ./data --admin-secret "$JAZZ_ADMIN_SECRET"`, with file-backed persistence to `--data-dir` (SQLite-backed on the current Node.js implementation per `https://jazz.tools/llms-full.txt`, confirmed live at [jazz.tools/docs/getting-started/server-setup](https://jazz.tools/docs/getting-started/server-setup)), an `--in-memory` flag for ephemeral/dev use, and configurable JWT/JWKS or local-first-auth validation. It requires Node.js 22.12+ for the built-in `node:sqlite` driver (`https://jazz.tools/llms-full.txt`). There's no official Docker image and no mention of Raspberry Pi or resource-constrained deployment in the docs — but a single Node CLI process with file-based SQLite storage is about as easy a thing to wrap in a `Dockerfile` and drop into an existing `docker-compose.yml` as this class of tool gets, which matches this project's actual deployment shape well. Classic Jazz's self-hosting story is described in less operational detail in what's publicly documented, but the same "single-tenant server, open source, easy to self-host" framing applies to it too.

Neither product's docs discuss running the sync server on genuinely constrained hardware (a Pi specifically), so that remains untested by anything found here — worth a real trial run before trusting it, not something to take on faith from the docs.

## 4. Anonymous device identity upgrading into a real verified account

This is the second pleasant surprise. Jazz v2 has this as one of its three named auth modes, not a bolted-on feature: `anonymous` (ephemeral, no writes), **`local-first`** — **"Stable identity from a device secret, no server needed"**, explicitly recommended for **"Production offline-first apps, try-before-signup"** — and `external` (JWT-based, for verified accounts) (`https://jazz.tools/docs/auth/authentication`, confirmed live). The documented upgrade path is exactly the shape this app needs: start on a local-first secret, later prove ownership of that identity to your server via `db.getLocalFirstIdentityProof(...)`, link it to the newly-created external account so its JWTs carry the *same* Jazz user ID as `sub`, then reconnect with the external credential — **"Users can start with local-first auth and later sign up with an external provider while keeping the same Jazz identity"** (`https://jazz.tools/llms-full.txt`, Lifecycle section, matching the live `/docs/auth/lifecycle` page). Because permission policies and all row ownership key off that stable Jazz user ID (not off which auth mode produced it), a player's rows don't need a separate re-keying/merge pass the way this app's current `email_hash` upgrade does — the identity doesn't change across the upgrade, so there's structurally nothing to re-key. That's arguably a cleaner mechanism than the one already planned in ADR-0009's now-folded design (which does need an explicit `UPDATE ... SET email_hash = ...` re-key step precisely because this app's anonymous and email identities are different hashes).

Classic Jazz's npm dist-tag history includes an old `guest-auth` prerelease tag, suggesting anonymous/guest auth existed there too at some point, but nothing found in this pass documents its current maturity or upgrade story as directly or as centrally as v2's local-first auth is documented — worth flagging as unverified rather than assumed absent.

## 5. Blast radius if adopted — layers affected, not a migration design

This would not be a client-storage-only change. Jazz's entire value proposition is being the shared source of truth across client and server, so adopting it for real would touch:

- **`apps/frontend/src/storage/trialHistory.ts` and `levelStats.ts`** — replaced outright; `localStorage` reads/writes become Jazz queries against locally-replicated tables/CoValues.
- **`apps/frontend/src/sync/pushResults.ts`** — the fire-and-forget `POST /sync/results` call disappears entirely; Jazz's local-first write model (write locally, sync in the background, retry on reconnect) is exactly the retry-queue-on-failure gap this file currently doesn't cover, so this is the piece Jazz most directly improves rather than merely relocates.
- **`apps/backend/src/routes/sync.ts` and `apps/backend/src/sync/logic.ts`** — the explicit `POST /sync/results` / `POST /sync/level-stats` endpoints go away as HTTP endpoints; the re-validation logic they contain would move into a Jazz server-worker process (Q2), still needing `packages/engine`'s scoring rules, just triggered by observing synced writes instead of by handling a request body.
- **The `trial_results`, `level_runs`/`trial_keystrokes`, and `level_stats` SQLite tables** — this is the biggest open question this research can't fully close. In v2, Jazz's own storage *is* a relational SQLite-backed store on the server (Q3), so the honest framing is that Jazz would likely become the source-of-truth store for this data, not a layer sitting in front of the existing hand-rolled tables. Whether `apps/backend/src/db.ts`'s existing tables survive as a separate admin/analytics read-replica, get dropped entirely, or get queried directly against Jazz's own SQLite file, isn't something the docs pulled in this pass settle — it would need to be worked out by whoever actually attempts this, not assumed here.
- **Practice sessions** — nothing found in Jazz's docs suggests it would erode the "practice is local-only, never synced" distinction; a Jazz-based redesign could just as easily keep practice data out of any synced table/CoValue entirely, the same way it's kept out of the sync payload today. This looks preservable, not naturally eroded, though it'd need to be a deliberate choice (don't `db.insert` practice trials into a synced table) rather than something Jazz forces either way.
- **Auth (`moravec_session` cookie, `proxy.ts`)** — would very plausibly be replaced or subsumed by Jazz's own auth modes (Q4), since Jazz's permission model needs to know the calling identity itself, not just receive an opaque cookie.

The honest characterization: this touches the client storage layer, both sync endpoints, most of the backend's sync-related schema, and likely the auth/session layer too. It is a full replacement of the sync architecture that ADR-0002 through ADR-0010 just finished building over the last two days, not an incremental addition next to it.

## 6. Rough edges and other concerns

- **Bundle size.** Bundlephobia measures the current `jazz-tools` (classic, `latest` = `0.20.19`) bundle at **406,754 bytes gzip** for its main asset, with `cojson-core-wasm` alone contributing over 1.2MB of the unminified dependency weight (`bundlephobia.com/api/size?package=jazz-tools`, live-queried). That's a meaningful addition to a frontend that's otherwise a fairly lean Next.js app. v2's equivalent figure wasn't retrievable in this pass (rate-limited before a second measurement completed) — treat classic's number as directionally informative, not as v2's actual size.
- **Conflict semantics vs. this app's data shape.** v2's model is field-level last-writer-wins with full row-version history retained — **"Even row versions that lose that race remain in row history"** (`https://jazz.tools/llms-full.txt`, How Sync Works) — which is a good structural match for "never drop trial data": nothing is discarded even when superseded. But Jazz explicitly does not do domain-aware merging: **"Jazz can resolve structural conflicts for you, but it cannot fully understand the meaning of your data"** (same source) — so the "more stars, or same stars + less time" LevelStats comparison this app already implements in `apps/frontend/src/storage/levelStats.ts` would still need to be hand-written as application logic on top of Jazz, not something Jazz gives you for free. Append-only writes (trial results, level runs) map cleanly onto Jazz's `upsert(table, data, { id })` primitive keyed by a client-generated ID — a close match for the dedup pattern this app's backend already uses via `INSERT OR IGNORE` on a client-generated UUID.
- **Pricing (context only, since self-hosting is the plan).** Jazz Cloud's published tiers ([classic.jazz.tools/pricing](https://classic.jazz.tools/pricing)): a free **Starter** tier (100 monthly active users, 10GB storage, 0.2GB sync egress), **Indie** at $4/mo (10,000 MAU, 100GB storage), and consumption-based **Pro** ($0.02/GB storage, $1.00/GB sync egress, $0.10/GB blob egress). At this app's scale, Jazz Cloud would cost nothing to very little if it were ever used instead of self-hosting — not a factor against adoption, just noted per the research brief.
- **Maturity/stability signals, summarized.** Classic Jazz: 3-year-old project, real if small-scale production usage, release cadence has visibly slowed as the vendor's attention shifted to v2, and the vendor's own stated plan is to eventually retire it once migration is broadly done. v2: under 8 months old as a public repo, shipped 49 alpha releases in that time, and its own announcement post uses the words "alpha-quality," "evolving API," and "best-effort SLA" about itself, with larger/commercial adopters explicitly gated to hand-held onboarding rather than open self-serve. Neither of those is "we said no when it was too soon and now it's obviously ready."

## Why "still too soon" rather than "conditionally yes"

The architecture fit questions (2, 3, 4) came back better than a skeptical prior would predict — this is a genuinely different picture than "CRDT merge is final, full stop" or "no self-hosting story" or "no anonymous-account support," any of which would have been a clean, easy no. If those had been the findings, this would be a clear "still too soon" with nothing more to say. Instead the case against rests entirely on the vendor's own characterization of production-readiness (Q1, Q6): v2 says of itself that it isn't done evolving, and classic Jazz is a maintained-but-being-phased-out product. For a self-hosted, single-maintainer app with no platform team to absorb an alpha SDK's breaking changes or to migrate off a sunsetting one, betting the sync layer — which was *just* rebuilt from scratch over the last two days (ADR-0002 through ADR-0010) — on either product right now trades a known, understood, working bespoke system for an unstable foundation, in exchange for sync guarantees (retry-on-reconnect, cross-device merge) this app doesn't yet have a concrete product need for beyond "would be nice."

**Concrete trigger to revisit:** either Jazz v2 reaching a stable/non-alpha release (its own docs, not secondhand commentary, dropping the "alpha-quality" language), or a specific product need emerging that the current bespoke sync genuinely can't satisfy (e.g., a real request for offline play with automatic cross-device reconciliation, which is exactly what local-first sync is for and what the current fire-and-forget push doesn't provide). Absent either of those, this is worth checking again in passing every few months, not worth spending implementation time on now.
