> **Partially superseded.** The anonymous-account idea this ADR named as future work (below) was later picked up and built: every player now gets a client-generated device-id session automatically, upgraded to a real email User on OTP login (see CONTEXT.md's Sync/User/Anonymous session entries). The level-unlock reasoning below is still the live decision, unaffected by that — level-unlock has not moved server-side.

# Defer anonymous device-id accounts and server-side level authorization

Giving Levels real routes (`/level/[levelNumber]`) raised a natural next question: since a level's URL is now typeable, should the backend decide whether a player is allowed to play it, the way it already independently re-validates trial correctness (ADR-0005)? The blocker is that today only email-verified players have a backend session at all — an anonymous player has no identity the backend could check anything against. The proposal on the table: make every player logged in, with email accounts kept for cross-device sync as today, and a device-id-based anonymous account for everyone else, so the backend has *someone* to authorize against either way.

We're not doing this now. Level-unlock has never been a security boundary — it's a local progression gate over a free game with no valuable resource behind it, and the existing trust model (`LevelStats` in `localStorage`, the whole premise of ADR-0002) already accepts that a player can edit their own record if they want to. A device id doesn't actually raise that bar: it's just another client-supplied value, exactly as easy to regenerate or spoof as clearing `localStorage` is today, so moving the *unlock* check server-side would add real backend surface (an anonymous-user table, a session-issuance endpoint with its own abuse/rate-limit story, an anonymous→email account-upgrade merge flow) for a boundary that wouldn't actually be any stronger. `/level/[n]`'s unlock check stays client-side, reading local `LevelStats`, same as the rest of the app.

The part of this idea actually worth keeping: anonymous accounts would be valuable for **continuity**, not enforcement. Today, a player who never logs in with email loses all progress the moment they switch devices — Sync (ADR pending none yet, see CONTEXT.md's "Sync" entry) only exists for email-identified Users. An anonymous session would let every player's progress sync across their own devices without ever giving an email, with the OTP flow becoming purely an *upgrade* path (claim a persistent identity, keep syncing) rather than the only door into syncing at all.

**If this gets picked up:** the backend would mint a session for a client-generated device id via a new unauthenticated endpoint (no OTP round-trip — that's the whole point of it being low-friction), store it against a `User` row with a nullable email hash instead of a mandatory one, and reuse the exact merge logic `mergeRemoteLevelStats` already implements for the email→email case to reconcile local progress when an anonymous session later claims an email. The frontend side is mostly already in place: ADR-0007's cookie-backed `authStore`/proxy validation model doesn't care how a token was issued, so an anonymous session would flow through the same `AuthState.loggedIn` shape OTP verification already produces today — no new client-side session model needed, just a new way to obtain the token. **Trigger for revisiting:** a concrete request for cross-device continuity without email, not a desire to gate levels — that motivation doesn't hold up on its own.
