# Migrate apps/frontend from Vite/SPA to Next.js App Router

The Vite app was a single-page, no-router SPA: one `App.tsx` derived a `CurrentScreen` from in-memory nav state plus the game/practice/auth stores, and `/admin` was reached only via a `window.location.pathname` check at mount. That was fine for a small game, but it meant no real URLs (nothing to bookmark, share, or reload into), no way to server-render anything, and every screen paid for every store's subscriptions whether it needed them or not. Per the grilling session, the migration target is real routing matching the app's five screens (`/`, `/stats`, `/practice`, `/login`, `/admin`), each a Next.js App Router route.

**Rendering is mixed, not uniformly server- or client-rendered.** Only `/admin` is a Server Component — it has no interactivity, and server-rendering it removes a client loading state entirely. Every other route is a Client Component: `/` hosts the level-selection grid and, embedded in the same route rather than a separate one, the Level gameplay state machine itself (ticket 07) — matching the old app's "gameplay is a screen the menu turns into," not a distinct URL. `/admin`'s Server Component fetch is dynamic (`export const dynamic = "force-dynamic"`), not Next's default static-at-build-time — confirmed live: without it, the build marked the route static (○) and would have served one build-time snapshot to every visitor forever.

**TanStack Query is scoped to component-rendered loading/error state, not every fetch.** Login's OTP request/verify (ticket 05) render pending/error state in the UI, so they're `useMutation`. Level-finish sync, the post-login LevelStats pull, and the admin fetch are all fire-and-forget or already-server-rendered — none of them have a component waiting on loading/error state — so they call `Api` directly, bypassing React Query entirely. The rule that emerged: reach for `useQuery`/`useMutation` only when a component actually needs to render that request's status.

**A single `Api` object (ticket 02) is the one place every backend call is defined** — a plain async function per endpoint, throwing on a non-ok response so the same function works as a direct call or a TanStack Query `queryFn`/`mutationFn` without adapting. This replaced several old scattered fetch call sites (`auth/api.ts`, `admin/fetchAdminStats.ts`, `sync/pull.ts`, `sync/push.ts`).

**The auth store was restructured twice.** First, slimmed (ticket 03): the login flow's own step-tracking/submitting/error state moved out of the global store and into the `/login` route's local state — it was never used anywhere else. Second, and not originally planned: `authStore`'s initial state read `localStorage` at store-creation (module-eval) time, which broke SSR hydration — the server always renders LoggedOut, but the client's module re-evaluates before hydration and can pick up a real session immediately, so any full page load with an existing session mismatched. Caught live while verifying ticket 08, not anticipated by any ticket. The fix: the store always starts LoggedOut and exposes `hydrate()`, called client-only from a mount effect, alongside `restoreSession()`. The same fix applied to `StatsScreen`'s trial-history reads, which had the identical bug. **Anywhere a Zustand store's initial state depends on browser-only storage, defer that read to a mount effect — never compute it at store-creation time.**

**Docker deployment (ticket 10) surfaced a second live-only bug**, also not anticipated: the frontend and backend are separate containers on their own network namespaces, so `/admin`'s server-side fetch — running *inside* the frontend container — couldn't reach the backend via `localhost`. `env.ts` now branches `API_URL` by execution context: the public, build-time-baked URL in the browser; a runtime-only `API_URL` env var (Compose's internal `http://backend:3000` service-name DNS) on the server.

Both of those were real bugs, not hypothetical — each one was only found by actually running the built app against a real backend, not by tests or by reasoning about the code. `pnpm build`'s static/dynamic route markers and a full container-to-container network test earned their place in the verification loop for exactly this reason.
