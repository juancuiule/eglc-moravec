# Local-first sync: append-only replication, no CRDT, TinyBase for local storage

Issue #5 asked for "CRDT-like" offline-first sync. Re-examining the actual data shapes (`trial_results`/`level_runs` are append-only event logs identified by a client-generated id; `trial_keystrokes` belongs to one trial; `level_stats` is a single scalar "more stars, less time wins" comparison) found no genuine multi-writer conflict to resolve — every device only ever produces new facts, never edits or deletes existing ones. So we decided against a document-CRDT library (Automerge/Yjs/Loro/Triplit) and against TinyBase's own CRDT-flavored `MergeableStore`/`Synchronizer`, adopting instead: a durable local write queue (retry/backoff via Effect, per the sketch in issue #5's first comment), a cursor-based pull keyed off a new server-assigned `server_seq` column per synced table, and TinyBase's plain `Store` + TinyQL query engine for local storage/reactivity — chosen over Dexie for its declarative `group`/`having` aggregation, needed because `level_stats` is no longer synced (see Consequences).

## Considered options

- **RxDB**: viable (bring-your-own-backend, pluggable per-collection conflict handler), but its reactive-query/collection model solves a bigger problem — arbitrary local queries over a general database — than this app needs once `level_stats` is a query, not synced state.
- **Automerge / Yjs / Loro / Triplit**: real document-CRDTs, built for concurrent structural edits to shared state by multiple writers. This app has neither multiple writers nor genuine conflicts, so all four cost more (bundle size, conceptual overhead, and for Triplit, AGPL-3.0 licensing risk) than they solve.
- **ElectricSQL / PowerSync / Zero (Rocicorp)**: each hard-requires a Postgres-family upstream as the sync source, forcing a backend database migration as a side effect of adding client sync. Rejected while the backend stays SQLite.
- **Jazz.tools**: previously rejected (see root `CONTEXT.md`); re-checked here and the verdict still holds — it's a full backend replacement (its own accounts/permissions/storage), not an add-on to the existing Fastify+SQLite backend.
- **Dexie**: the closest real alternative to TinyBase — same zero-runtime-dep, IndexedDB-backed, permissive-licensed shape. Its `Collection` API (`where`/`filter`/`orderBy`) has no declarative aggregation: "best stars+time per level" would need `.toArray()` plus hand-written JS reduction, and its own re-run/memoization logic layered on `dexie-react-hooks`' raw-callback reactivity. TinyBase's `Queries` object (`select`/`where`/`group`/`having`) does this declaratively and reactively out of the box — the deciding factor for this specific shape.

## Consequences

- `trial_results` gains a client-generated **`run_trial_id`** column (unique, `INSERT OR IGNORE` dedup key), matching the idempotency role `level_runs.id` already plays. `trial_results.id` itself stays `AUTOINCREMENT` — unlike `level_runs`, a trial and its `trial_keystrokes` are always inserted together in one request via `lastInsertRowid`, offline batches included, so nothing needs to know `trial_results.id` before the backend assigns it. The client id's only job is letting a retried push skip rows it already stored.
- `trial_results` and `level_runs` each gain a **`server_seq`** column: a monotonically increasing integer assigned by the backend at write-acceptance time (whether the write arrived live or via a queued offline push), used purely as the pull cursor — a client sends the highest `server_seq` it's already seen per table and gets back everything newer. `trial_keystrokes` doesn't need its own — it's always pulled nested under its parent `trial_results` row, never paginated independently.
- The backend gets real `FOREIGN KEY` constraints (`PRAGMA foreign_keys = ON`) for the first time. Every relationship today (`trial_results.email_hash` → `users.email_hash`, `trial_keystrokes.trial_result_id` → `trial_results.id`, etc.) is convention-only, held together by indexes, not enforced by SQLite. Not enforced client-side — the local store is a write queue/cache, not the system of record.
- `level_stats` stops being a synced/stored table entirely. It becomes a query — "max stars, then min time, per level" — computed on demand from `level_runs`, both locally (TinyQL) and server-side.
- This design assumes no `trial_results` / `level_runs` / `trial_keystrokes` row is ever edited or deleted after being written. If a deletion path is ever needed (a GDPR request, an admin correction), it requires a deliberate mechanism — e.g. an append-only tombstone record — since the whole "no conflict" argument depends on pure accumulation holding.
- Anonymous → logged-in re-keying is still an open design question: how a locally-queued, not-yet-pushed write gets its `email_hash` rewritten when an Anonymous session upgrades mid-queue. Not resolved by this ADR.
- Sync topology is backend-hub only: devices never sync with each other directly, only push to and pull from the backend.
- The Level catalog (`levels` table) needs none of this — it's shared, backend-owned, effectively static, publicly readable, and already a plain cache-and-refresh concern regardless of tool choice.
