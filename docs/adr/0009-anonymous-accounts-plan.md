# Anonymous device accounts and the upgrade-to-email flow

This is the concrete design for the idea ADR-0008 named but deliberately deferred: every player gets a session from first launch, email accounts stay for cross-device continuity, and OTP verification becomes an *upgrade* of an existing anonymous identity rather than the only door into syncing. It is a plan, not yet a build — the schema and endpoint sketch below are ready to implement, but the actual product-shape calls (does every player silently get an anonymous session on first launch, or only once they try to leave a device? what does the upgrade prompt say and when does it appear?) are for whoever picks this up to confirm before writing code, not something to infer from this document alone.

**Identity storage needs no schema migration.** Every table in `apps/backend/src/db.ts` (`users`, `sessions`, `trial_results`, `trial_keystrokes`, `level_stats`) keys off `email_hash` as an opaque string — nothing downstream cares that it happens to be derived from an email today. An anonymous identity can reuse the exact same column by hashing a client-generated device id (a UUID minted once on first launch, persisted the same way `moravec_session` already is) through a sibling of `hashEmail` in `apps/backend/src/auth/logic.ts` — call it `hashDeviceId` — namespaced with a fixed prefix (e.g. `HMAC(secret, "device:" + deviceId)` vs. today's `HMAC(secret, normalizeEmail(email))`) so a crafted device id can never collide with a real email's hash. Every existing repo function (`upsertUser`, `createSession`, `getSession`, and the sync repo's trial/level-stats functions) works unmodified — they already only see the resulting hash string, not where it came from.

**New endpoint: `POST /auth/device`.** Unauthenticated, no OTP round-trip (that's the point — zero friction). Body: `{ deviceId: string }`. Hashes it, calls the existing `upsertUser` + `createSession`, returns the same `{ token }` shape `/auth/otp/verify` already returns. The frontend's `authStore` (ADR-0007) doesn't need a new state shape for this — it's still just `AuthState.loggedIn` with a token, exactly as OTP verification produces today. What's new on the frontend is *when* this fires: something needs to call it on first launch if no session cookie exists yet, before proxy.ts's existing validation logic even applies.

**The upgrade merge is two separate operations, not one.** `level_stats` needs the same better-record comparison `mergeRemoteLevelStats` (`apps/frontend/src/storage/levelStats.ts`) already does client-side for the ordinary email→email login case — but here it needs to happen once, server-side, at the moment of upgrade, so a *different* device logging into the same email later sees the merged result rather than needing to replay the merge itself. That means porting the comparison (more stars wins; same stars, less time wins) into a backend equivalent, invoked from `/auth/otp/verify` when the request carries an existing anonymous session's identity to upgrade from. `trial_results` and `trial_keystrokes` are append-only history with no "best record" concept, so those rows just get re-keyed from the anonymous `email_hash` to the newly-verified one — a plain `UPDATE ... SET email_hash = ? WHERE email_hash = ?`, no merge logic needed. After both run, the anonymous row in `users` is orphaned and can be deleted or just left — it's never looked up again once its session token is gone.

**What `/auth/otp/verify` needs to know to trigger this**: the anonymous session's token, so it can resolve the anonymous `email_hash` before overwriting the session cookie with the email-identified one. The simplest shape is the client sending its current (anonymous) `Authorization` header on the verify request, same as any other authenticated call — no new request field needed, just a check in the verify handler for whether the bearer token resolves to an existing session before minting the new one.
