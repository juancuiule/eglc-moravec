# Moving Level definitions to the backend

`LEVELS` (`apps/frontend/src/LEVELS.ts`) is a 1,357-line static map from level number to weighted Operation-category distribution, imported directly into client code and used at two very different points: `/level/[levelNumber]/page.tsx` (a Server Component) checks a level number exists in it to decide `notFound()`, and `LevelPlay`/`createRandomOperation` (`apps/frontend/src/level.ts`) reads a level's weights on every trial to draw the next Operation client-side. The backend today has zero knowledge of level content at all — `sync/logic.ts` re-validates trial *correctness* (ADR-0005) using `levelNumber` as an opaque number, never checking it against a real catalog. This is a plan for what moving the catalog server-side would actually touch, not a decision that it should happen now — the real motivations (redeploying content without a frontend build, or per-cohort level variation for research, given Moravec's origins as a research instrument — see `CONTEXT.md`) are worth confirming are still wanted before building this, since the backend works fine without it today.

**Don't reach for a database table first.** Nothing about this data needs to be user-editable at runtime or queried relationally — it's config, read wholesale, rarely written. A `levels` DB table buys runtime editability (an admin UI to tweak weights without any deploy) at the cost of a schema, migration, and admin surface that isn't justified unless that specific need shows up. The lower-cost move that still captures the main win — changing level content without shipping a new Next.js build — is relocating `LEVELS.ts` into `apps/backend/src` as a plain TS module and serving it through a route. If live editability becomes a real ask later, that route's implementation can swap to a DB read without the frontend or its contract changing at all.

**Two new endpoints, matching the two ways the frontend already reads `LEVELS`.** `GET /levels` returns the level-number list plus whatever minimal metadata Home's grid needs (today just "does it exist" — Home derives unlocked/locked from local `LevelStats`, not from the catalog, so this can be a thin list, not full weight data). `GET /levels/:levelNumber` returns one level's full weighted category distribution — the only place that needs the heavy payload.

**The natural fit is exactly where the code already branches on `LEVELS`.** `/level/[levelNumber]/page.tsx` is already a Server Component doing a `notFound()` check against `LEVELS` — swap that check for a server-side fetch to `GET /levels/:levelNumber`, and thread the resolved `Level` down as a prop to `LevelPlay` instead of `LevelPlay` importing the static map itself. That's a strict improvement even independent of the backend move: it turns "level doesn't exist" from a client-bundled data check into a real server-resolved 404, and it means gameplay only ever fetches the *one* level being played, not all 1,357 lines. Home (`app/page.tsx`) is already a Client Component (it has to be — it reads `localStorage` via `loadLevelStats` to render the unlocked grid), so its catalog list fetch stays client-side, most naturally via the same TanStack Query pattern already used elsewhere in the app for fetches with loading/error state.

**What doesn't change:** the actual per-trial random draw (`createRandomOperation` in `level.ts`) stays entirely client-side, using whatever `Level` config was already fetched for the level in play — there's no reason to round-trip to the server on every trial, and doing so would work against the app's local-first, offline-tolerant gameplay loop. Only the *lookup* of a level's config moves server-side; drawing from it doesn't.
