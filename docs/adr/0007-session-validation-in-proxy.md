# Move session validation into proxy.ts; cookie-backed session

ADR-0006 fixed the auth store's SSR hydration bug by having a client-mounted `restoreSession()` validate a persisted session against the backend, right after `hydrate()` read it from `localStorage` — correct, but it meant every page load carried a client-visible fetch whose entire purpose was "is this session still good," plus a one-tick logged-out flash before it resolved.

Server Components can't fix this on their own: `cookies().set()`/`.delete()` throw outside a Server Action, Route Handler, or proxy — a Server Component can *read* a cookie but can never clear an invalid one during render. Proxy (`apps/frontend/proxy.ts`, née `middleware.ts` — renamed by Next.js 16) is the tool built for exactly this: it runs server-side, before any route renders, and can both read and write cookies.

Session persistence moved from `localStorage` to a cookie (`storage/session.ts`, still browser-only — written at login, read/deleted client-side at logout, all unchanged in spirit from ADR-0006). `proxy.ts`, scoped to `/` and `/login` only (the two routes that render differently based on auth), reads that cookie and calls the backend's `/auth/me` itself, deleting the cookie on the response if it's invalid. Prefetch requests (Next prefetches every in-viewport `<Link>` by default) are skipped, since this runs against a single self-hosted backend instance.

The auth store's `restoreSession()` is gone entirely. `hydrate()` remains — it's still a client-mounted effect reading a client-only source (`document.cookie`) into the Zustand store, for the same reason ADR-0006 gave: reading it at store-creation time would still disagree with the server-rendered HTML. The difference is what it's *for* now: by the time `hydrate()` runs, proxy.ts has already guaranteed the cookie is either absent or valid, so `hydrate()` is a synchronous local parse, never a network call. Verified live: reloading `/` while logged in, revisiting `/login` while logged in, and reloading with a deliberately tampered cookie all produce zero client-side requests to `/auth/me` — the tampered case gets its cookie cleared server-side before the page renders at all, no flash of a stale logged-in state.

The session cookie is not `httpOnly`. Client code still needs to read the token itself to attach `Authorization: Bearer` headers on calls the backend expects (sync push, LevelStats pull) — an `httpOnly` cookie would block that, and would require proxying every such call through the frontend's own server (Route Handlers or Server Actions) to attach the header on the client's behalf. That's a real hardening option if XSS-resistance on the token becomes a priority; it wasn't the ask here, and it's a materially larger change than this ticket.
